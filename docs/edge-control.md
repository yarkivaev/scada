# Edge assignment control

Three independent edge clusters run etcd and controller replicas; every collector embeds an assignment agent. Losing the control majority prevents new placement but never expires saved work. Serial tasks require a pinned node. Controller changes use etcd transactions comparing the leader value and lease.

Controller environment: CONTROL_NODE_ID, CONTROL_ENDPOINTS (comma-separated), CONTROL_PREFIX (default /scada/control), CONTROL_CA, CONTROL_CERT, CONTROL_KEY, CONTROL_USERNAME, CONTROL_PASSWORD, CONTROL_REPLACEMENT_DELAY_MS (default 30000), CONTROL_CLOCK_SKEW_MS (positive finite milliseconds, default 5000). Run `scada-controller`.

Collector environment: COLLECTOR_NODE_ID, COLLECTOR_CONTROL_ENDPOINTS, COLLECTOR_CONTROL_PREFIX, COLLECTOR_CONTROL_CA/CERT/KEY, COLLECTOR_CONTROL_USERNAME/PASSWORD and COLLECTOR_ASSIGNMENT_FILE (persistent volume). Run `scada-collector`. Existing manifest mode is unchanged when control endpoints are absent. The entire snapshot is validated and fsynced before execution; offline startup restores it. Errors applying one snapshot are retried and reported without discarding the saved assignment. The health endpoint is independent of etcd availability.

`@yarkivaev/scada/control` exports `clientFromEnv`, `controlStore`, `publishCatalog`, `schedule`, `controller` and `assignmentAgent`. Publish with `publishCatalog(controlStore(clientFromEnv(env), env.CONTROL_PREFIX), catalog, expectedRevision?)`. Catalog shape:

```json
{"version":"1","nodes":[{"id":"edge-a","capacity":100}],"tasks":[{"taskId":"plant/channel","copies":2,"cost":1,"eligibleNodes":["edge-a"],"spec":{"adapter":"example"}}]}
```

`pinnedNode` forces one physical host. Network tasks default to two copies and capacity cost one. Placement preserves current owners; coverage of each source precedes second copies. Source reading progress is separate from process heartbeat. Extra copies are removed only after enough remaining copies confirm recent reads. An unreachable owner retains its saved work.

Telemetry payloads, credentials, task specs and delivery addresses must not appear in public health responses or error logs. Production etcd must use authenticated TLS plus enabled etcd auth with per-node prefix permissions. The JSON gRPC gateway does not support client-certificate CN as an RBAC identity: it requires username/password authentication at /v3/auth/authenticate and an Authorization token. The client caches tokens for at most 60 seconds and retries authentication once on an invalid/expired token response. Passwords belong in Kubernetes secret references; controller, publisher and individual agents use distinct identities. Neither credentials nor token payloads are included in errors. TLS client verification remains enabled independently of RBAC. Catalog publishers and controllers need separate credentials. Provisioning belongs to the deployment DSL.

The gateway request deadline defaults to two seconds per endpoint and response capacity to eight MiB. Initial catalogs should remain small enough to fit etcd transaction limits; this implementation uses one fenced transaction per reconciliation. After restoring an older etcd snapshot, publish the catalog with a new nonempty `controlEpoch`. Agents accept the new epoch and persistently rebase local execution generations above prior values. Within one epoch, stale generations remain rejected. Reports map local execution generations back to remote task generations for controller readiness checks.

Verification: `npm test`, `npm run lint`, and `node test/integration/controlEtcd.js` against disposable etcd at ETCD_TEST_URL. The control integration workflow runs only on pull requests and never deploys.

The disk spool has two admission bounds: `COLLECTOR_SPOOL_MAX_BYTES` and `COLLECTOR_SPOOL_MAX_RECORDS` (positive safe integer, default 100000). Existing records are never evicted to admit new observations. Partial recipient confirmation does not release a record slot; full confirmation does. Startup reads directory entries incrementally and refuses to open an existing spool exceeding the configured record bound, preserving every file; raise the bound to recover and drain that backlog. Status exposes `recordLimit` alongside pending count and byte usage.

## Durable local telemetry receivers

Set `HISTORY_AMQP_ENABLED=true` on each edge receiver application, with `HISTORY_AMQP_URL` (or `AMQP_URL`), `HISTORY_AMQP_QUEUE` (default `scada.telemetry.history`) and mandatory explicit JSON `HISTORY_AMQP_BINDINGS`. The node-owned PostgreSQL receiver starts after migrations even when movable collector pipelines are external. It consumes persistent AMQP telemetry independently of expiring MQTT sessions, and acknowledges each message only after the PostgreSQL metrics insert and history trigger transaction finish. Automatic MQTT-to-PG ingestion is disabled in this opt-in mode; live supervisor MQTT classification is independent. Payloads must carry their original integer millisecond `ts` and finite numeric `value`; malformed messages do not receive successful acknowledgement.

Producer AMQP descriptors supply `options.queues` and `options.bindings` alongside `options.exchanges`. These are asserted before publishing becomes active, so a receiver that has never connected still has its durable queue. Local history queue declarations use durable true and autoDelete false, with no TTL/overflow discard. A different matching queue, such as a central outbox, is insufficient proof of local delivery. The DSL emits intended local queues/bindings on each recipient descriptor. Grouped Modbus RTU tasks can filter recipient descriptors by `routingKeyPrefix`, so each furnace receives its own measurements directly; no matching recipient is an explicit failure, never silent loss.

### Read evidence and clocks

Read confirmation is valid only for the assigned task generation and current control epoch, with a running task and a recent read timestamp no more than the clock-skew budget ahead of controller time. Report liveness uses the same bound (5 seconds by default, configurable with CONTROL_CLOCK_SKEW_MS). Normal bounded positive or negative clock offsets remain eligible. Controller and executor clocks must be synchronized within this bound; larger forward jumps or stale timestamps can prevent new placement and rolling progress; saved assignments continue executing offline. Report receipt age currently uses executor wall time, so clock synchronization is an explicit operational prerequisite.

### Raw telemetry first choice

The local history AMQP receiver enables atomic first-write-wins receipts for `(topic, ts)` before topic registration. Generic `amqp-pg-metrics` and `mqtt-pg-metrics` assignments opt in with `firstWins: true`; default ingestion behavior is unchanged. Receipts, raw metrics and history-trigger work commit together before acknowledgement. Existing raw rows are preserved when enabling the policy; a legacy timestamp with multiple conflicting rows cannot recover which value originally arrived first. Apply edge migrations E0007 and privileged E0008 before enabling the policy. Retention deletes a receipt only beyond the configured history window (at least 30 days without mappings) and once its raw metric is gone; size persistent storage accordingly.

Placement-policy edits retain the existing reader on an ineligible or retiring node until the full desired count of eligible replacements confirms current-generation, matching-spec reads. Starting a replacement alone does not revoke the old reader. Explicit task deletion still revokes it. Rolling edits of replicated tasks preserve their only healthy reader and update a failed replica first when available; one-copy resource-pinned tasks require an in-place restart for configuration changes.

Historical correction contexts use at most 250 complete raw timestamp groups per page. Edge migration E0009 adds the durable work cursor and dependency end. A page commit checks the work token, cursor and context revision, writes its bounded correction, and atomically advances the cursor with a new token; only the final page retires the work. A lost response is recovered by polling the durable cursor. New observations reset the affected claim so a restarted worker recalculates from complete stored parameter and prior-segment seeds. Pending work protects the dependency envelope and predecessor anchors from retention. Original annotation extents survive partial pages, with current operator metadata authoritative.

Use the companion supervisor candidate with the E0009 core candidate. Stop/restart old history workers before enabling the upgraded history mode during a coordinated rollout: old workers do not pass continuation cursors or bound outward overlays, and the API rejects any segment extending beyond its page. Individual oversized timestamp groups or more than 10000 annotations in a page remain explicit capacity errors; ordinary long histories continue through durable pages. No deployment is performed by these review branches.
